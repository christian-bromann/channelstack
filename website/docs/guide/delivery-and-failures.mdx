# Delivery and failures

This page shows how to test the parts of a platform apps most often get wrong: retried and redelivered events, forged requests, rate limits, dropped connections and an uninstall. Everything here works against the fakes only. In [live mode](/docs/guide/live-mode) an action has no delivery to test, so these tests need a guard to skip there: see [Fake only](#fake-only).

## What the fakes send

Each fake delivers events the way its platform does: signed over the exact bytes it sends, within the platform's ack window, and retried on the platform's schedule.

| Platform | Signature                                                                                    | Replay protection                                                           | Ack window | Retries                                                                                                                                                       | Same event, again             |
| -------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Slack    | `X-Slack-Signature: v0=…`, an HMAC-SHA256 of `v0:<timestamp>:<body>` with the signing secret | `X-Slack-Request-Timestamp`; receivers refuse one more than 5 minutes old   | 3 s        | Right after a failed attempt, then after 1 and 5 minutes, with `X-Slack-Retry-Num` and `X-Slack-Retry-Reason`. An answer with `X-Slack-No-Retry: 1` ends them | Same `event_id`               |
| GitHub   | `X-Hub-Signature-256: sha256=…` with the webhook secret, and the older `X-Hub-Signature`     | None                                                                        | 10 s       | None; redelivery comes from the App's delivery log                                                                                                            | Same `X-GitHub-Delivery` GUID |
| Linear   | `Linear-Signature`, a hex HMAC-SHA256 of the body                                            | `webhookTimestamp` in the body; receivers refuse one more than a minute old | 5 s        | After 1 minute, 1 hour and 6 hours, stamped and signed again                                                                                                  | Same `Linear-Delivery` id     |
| Notion   | `X-Notion-Signature: sha256=…` with the verification token                                   | None                                                                        | 5 s        | Up to 8 times over about a day, with `attempt_number` in the body                                                                                             | Same event id                 |
| Resend   | Svix's: `svix-signature: v1,…`, a base64 HMAC-SHA256 of `<svix-id>.<svix-timestamp>.<body>` with the `whsec_` secret | `svix-timestamp`; receivers refuse one more than 5 minutes old | 15 s | After 5 seconds, 5 and 30 minutes, 2, 5, 10 and 10 hours, signed again each time | Same `svix-id` |
| Google   | `Authorization: Bearer <OIDC token>`, RS256, from Pub/Sub's push service account, for the push endpoint as audience; checked with `verifyIdToken` against `GOOGLE_CERTS_URL` | The token's `exp`: an hour after it was issued, with 5 minutes' skew | 10 s | Pub/Sub's push backoff, from 100 ms up to a minute. Gmail pushes at most once a second per mailbox ([Google](/docs/platforms/google#one-push-a-second)) | Same Pub/Sub message id |

Over Slack's Socket Mode there is no signature, because the connection is the app's own, and a retry carries `retry_attempt` and `retry_reason` in the envelope.

## Deliveries in a test

An action that reaches the app gives you the delivery it caused:

<Example id="delivery-handles" />

A delivery has its `attempts`, each with the request headers, the app's response status and body, and how long the app took. Its `status` is the latest attempt's:

| Status         | Meaning                                     |
| -------------- | ------------------------------------------- |
| `pending`      | Queued or in flight                         |
| `acknowledged` | The app answered 2xx in time                |
| `failed`       | The app answered, but not 2xx               |
| `timed_out`    | The app didn't answer within the ack window |
| `unreachable`  | The app's URL couldn't be reached           |

`delivery.settled()` waits until the latest attempt has a final status. `msg.delivery` is `undefined` when nothing was sent: the app isn't in the channel, isn't installed or connected, or the server has no URL for the app ([connecting your app](/docs/guide/connecting-your-agent#tell-the-server-where-the-app-listens)).

## Slack's retry

<RetryTimeline />

Slack expects an acknowledgement within 3 seconds. An app that does its work before answering the HTTP request misses that window, and Slack sends the same event again. An app that doesn't notice answers twice.

<Example id="delivery-slack-retry" />

`retry()` sends the event again the way Slack does: the same payload and `event_id`, with `X-Slack-Retry-Num` and `X-Slack-Retry-Reason`. `after` defaults to 3 seconds, Slack's first retry, and `reason` to `http_timeout` (`http_error` and `too_many_redirects` are the others). The exact-count check then waits for the app to be quiet, so a second answer has time to show up.

The test proves the app is idempotent on `event_id`. The usual fix is to acknowledge at once and remember the event ids already handled. Bolt for JavaScript acknowledges events as they arrive unless `processBeforeResponse` is on, which is common on serverless hosts; with it on, a slow handler misses the window.

## Redelivery

A redelivery is the same event again, without anything that marks it as a retry. GitHub sends one when someone clicks Redeliver in the App's settings, Linear, Notion and Resend when the first delivery failed, Pub/Sub when a push wasn't acknowledged, and Discord's Gateway when a bot resumes a dropped connection and is sent what it missed:

<Example id="delivery-github-redeliver" />

| Platform | Call                   | What the app gets                                                                 |
| -------- | ---------------------- | --------------------------------------------------------------------------------- |
| Slack    | `delivery.resend()`    | The same event, same `event_id`, no retry headers                                 |
| GitHub   | `delivery.redeliver()` | The same webhook with the same `X-GitHub-Delivery` GUID, as from the delivery log |
| Linear   | `delivery.redeliver()` | The same webhook, stamped with a new `webhookTimestamp` and signed again          |
| Notion   | `delivery.redeliver()` | The same event again                                                              |
| Resend   | `delivery.redeliver()` | The same webhook with the same `svix-id`, signed again at its own time            |
| Google   | `delivery.redeliver()` | The same push with the same message id, with a fresh token                        |

## Bad signatures and stale timestamps

An app must refuse a request it can't verify. `resend` sends the delivery again with a twist, and `toBeRejected` checks that the app answered it with a 4xx:

<Example id="delivery-bad-signature" />

| Option               | What it sends                                                                                            | Platforms                     |
| -------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `badSignature: true` | The same body, signed with a secret that isn't the app's                                                 | Slack, GitHub, Linear, Notion, Resend, Google (a token another key signed), Discord (an interaction over HTTP, signed with another Ed25519 key) |
| `stale: true`        | Signed correctly, but with a time outside the replay window: 6 minutes old on Slack and Resend, 2 minutes on Linear; on Google, a token that has expired | Slack, Linear, Resend, Google |
| `wrongAudience: true` | Signed correctly, but a token for another endpoint than the app's | Google |
| `headers`            | Extra or replaced headers for this attempt                                                               | Slack                         |

`toBeRejected` reads the latest forged attempt. It fails when the app answered 2xx, and it tells you to call `resend` first when no forged attempt was sent. A forged attempt never counts toward `toBeAccepted` or `toBeRetried`.

Most SDKs verify signatures for you (Bolt, Probot, `@octokit/webhooks`, `LinearWebhookClient`), so these tests mostly catch an app that turned verification off, or one that reads the body before the SDK can check it.

## Acknowledging in time

`toBeAccepted` checks that the app answered 2xx, and with `within`, that it did so that fast:

<Example id="delivery-slash-command-ack" />

It reads the first real attempt. Without `within`, the platform's ack window is the limit, because an attempt answered after it is `timed_out`, not `acknowledged`. The same check works on a modal submission (`await modal.submit(…)`), a click and a shortcut.

`toBeRetried` is the other side: the delivery needed more than one attempt, because the app didn't acknowledge the first in time. `{ times }` makes it exact, and an exact check waits for quiet. `.not.toBeRetried()` is a short way to say the app was fast enough that the platform never retried. Retries you sent yourself with `retry()` count as attempts too.

## Faults

`slack.fault` makes the fake Slack Web API misbehave in a way the app has to handle:

<Example id="delivery-rate-limit" />

| Fault         | Options                                                             | What the app sees                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rate_limit`  | `operation`, `retryAfter` (default 1 s), `times`                    | HTTP 429 with `Retry-After`. The session stays busy until the app retries, so the checks wait for it ([waiting and quiet](/docs/guide/waiting-and-quiet#the-quiet-window)) |
| `error`       | `operation` (required), `error` (default `internal_error`), `times` | The call fails with that Slack error code, for example `msg_too_long`                                                                                                      |
| `latency`     | `operation`, `delay`                                                | Each call takes `delay` longer                                                                                                                                             |
| `drop_socket` | `after` (default: now)                                              | The Socket Mode connection drops once. A Socket Mode app should reconnect                                                                                                  |

Without `operation`, a fault applies to every Web API method; without `times`, to every call until it's undone.

<Example id="delivery-socket-drop" />

A fault lasts until `fault.undo()`, the end of an `await using` scope, or the end of the test's session, whichever comes first.

> [!WARNING]
> A fault applies to the whole workspace, not only to the test that set it: there is one app, and its calls belong to no session until they finish. While a fault is in effect, other tests running at the same time see it too. Put fault tests in a file of their own and run it in a separate `vitest run`, so nothing else runs alongside.

## The uninstall

When a workspace removes the app, Slack sends `app_uninstalled` and `tokens_revoked`. The app should acknowledge both and drop what it stored for the workspace:

<Example id="delivery-uninstall" />

The app is installed again, with the same tokens, when the test's session closes. Like a fault, the uninstall affects every test running at the same moment, so run it on its own. On GitHub, `repo.uninstallApp(github.app)` removes the App from one repository and resolves to the `installation_repositories` delivery.

## Fake only

Live, the real platform delivers to your app and channelstack isn't in the path. An action has no delivery: `msg.delivery`, `comment.delivery` and `session.delivery` are `undefined`, so nothing is refused and nothing skips on its own. The `!` in the examples above throws a `TypeError` live. A test that must also run live checks first, and skips:

<Example id="delivery-live-skip" />

The rest is refused, and Vitest and pytest skip the test with the reason:

- `slack.fault()` and `fault.undo()` with `action_requires`: a fault needs proxy mode, which live doesn't read the app's calls back yet ([#24](https://github.com/christian-bromann/channelstack/issues/24)).
- `slack.uninstallApp()`, and reading or resending deliveries (`slack.deliveries()`, `linear.deliveries()`, `notion.deliveries()`, `resend.deliveries()`, `google.deliveries()`, `discord.deliveries()`, `delivery.retry()`, `delivery.resend()`), with `unsupported_in_live`.

The same test runs in full against the fake on every pull request.

GitHub is the exception, because its App delivery log has an API: live, `github.deliveries()`, `toBeAccepted` and `delivery.redeliver()` work on the deliveries it lists, against a real test org, a few seconds after GitHub delivered. A comment's own `comment.delivery` is still `undefined` live. See [live mode](/docs/guide/live-mode).
