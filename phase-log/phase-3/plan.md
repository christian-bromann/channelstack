# Phase 3 plan

Goal: the GitHub fake. Every fake GitHub example passes against Probot and the Chat SDK's GitHub adapter.

## Exit checks → work

| Exit check | Test file(s) that prove it | Modules touched or created |
|---|---|---|
| 3.1 Every fake GitHub example passes | `api/examples/github.test.ts`, everything but "live mode", unchanged, against `examples/agents/probot` and `examples/agents/chat-sdk-github` (`pnpm test:accept`; `scripts/examples.ts` enables the GitHub blocks and runs them per GitHub agent) | `server/src/drivers/github/`, `integrations/matchers-core/` (the GitHub matchers), `integrations/vitest/` (the `github` fixture), `examples/agents/` |
| 3.2 Responses match GitHub's REST description | `server/src/drivers/github/github-conformance.test.ts`: a scenario that calls every route of the fake and validates each response against `@octokit/openapi` (`api.github.com`). `test/acceptance/github-schemas.setup.ts`: after every acceptance test, every API call the reference agent made, read back from the event log, validates too | `server/test/github-schemas.ts` (the one validator both use) |
| 3.3 Webhooks match GitHub's schemas | The same two files: every delivery the scenario and the acceptance run produced validates against `@octokit/openapi-webhooks` | `server/src/drivers/github/payloads.ts` |
| 3.4 Standard checks | `test/acceptance/checks/github-checks.test.ts`: `githubChecks({ app: "my-agent", … })` passes against both agents; `test/acceptance/checks-broken.test.ts`: each GitHub check fails against `examples/agents/broken-github` with that fault | `integrations/checks/`, `examples/agents/broken-github/` |
| 3.5 The fake signs like GitHub | `server/test/integration/github-delivery.test.ts`: delivery cases G1 to G3 against the running fake, received by `@octokit/webhooks` | `server/src/core/signing/github.ts` |

## Order of work

1. Driver skeleton: definition, secrets (webhook secret, the App's private key, an installation token), the org, the App and its installation, people. `GET /app`, installation endpoints and tokens, App JWT verification.
2. The git store: repos with blobs, trees, commits and refs; contents and the Git Data API; `push`, `readFile`, `commits`.
3. Issues: open, edit, close, comment, labels, assignees, reactions; `issues` and `issue_comment` webhooks; signing, GUIDs, the delivery log and redelivery.
4. Pull requests: open, files with patches, reviews and review comments with threads, review requests, ready for review, merge; their webhooks.
5. Check runs and statuses; `check_run` webhooks, Re-run and requested actions.
6. Control API routes, generated SDKs, the `github` fixture, the GitHub matchers.
7. Conformance (3.2, 3.3) and delivery cases (3.5).
8. Reference agents (Probot, Chat SDK) and the examples (3.1).
9. `githubChecks()` and the broken agent (3.4).
10. Docs.

## Reuse

| Concern | Module | Note |
|---|---|---|
| Sending webhooks, attempts, redelivery, forged signatures | `server/src/core/delivery/` | As Slack uses it. GitHub doesn't retry on its own, so no `RetryPolicy`; `redeliver()` is `again` with the same GUID |
| HMAC and constant-time compare | `server/src/core/signing/hmac.ts` | new: `signing/github.ts` adds `X-Hub-Signature-256` on top of it, as the code map plans |
| Ids | `server/src/core/ids/` | The `github.*` formats exist since phase 0. Issue numbers per repo and node ids are added here, not in the driver |
| Secrets | `server/src/core/secrets/` | `github.webhookSecret` and `github.installationToken` exist; new format `github.privateKey` (an RSA key generated by Node's crypto, kept in `secrets.json` like the others) |
| Sessions, ownership, the registry | `server/src/core/sessions/`, `registry/` | Repos, people, issues belong to the session that made them; the org, the App and its installation are world-level |
| Event log, API call records, quiet | `server/src/core/events/`, `quiet/` | The same middleware pattern as the Slack fake's API |
| Routes, waits, `retryWhile`, `onceQuiet` | `server/src/core/router/`, `codegen/` | `waitForComment`, `latestComment`, `headCommit()` are binding options that exist |
| Matcher plumbing | `integrations/matchers-core/` (`settle`, `fromMatches`, `textMatches`) | The GitHub matchers are new entries built on it; `toBeAccepted`, `toBeRejected`, `toHaveReceivedCall` are shared already |
| Standard checks | `integrations/checks/` | `githubChecks()` next to `slackChecks()`; the registration helper is shared |
| The stack for acceptance runs | `scripts/lib/stack.ts`, `scripts/examples.ts` | Extended to start a GitHub agent with its webhook path |
| new: `server/src/drivers/github/` | The driver, with the files every driver has | `fake/git.ts` (the git store, with patches and which lines a review comment may be on), `fake/api/*.ts` (the REST surface, one file per area) |
| new: `server/test/github-schemas.ts` | Validates a response or a webhook against GitHub's published schemas | Test-only; nothing in the binary reads the schemas |
| new: `examples/agents/shared/github.ts` | What both GitHub agents do (triage, duplicate, fix, review, check) | The same reason as `shared/workflows.ts`: the agents must behave the same |
