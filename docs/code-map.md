# Code map

> The one place that says **where each piece of shared logic lives**. Before writing a function, look here. If what you need exists, use it. If it almost exists, extend it. Only create a new module when nothing here fits, and add it to this map in the same PR.
>
> Planned paths are marked *(planned)* until the phase that builds them. The phase review checks that this file matches the code.

## Rules

1. **One owner per concern.** Every row below has exactly one module. Two implementations of the same concern is a blocking review finding.
2. **Drivers don't share code with each other.** Shared behaviour moves into `server/src/core/`. A driver importing from another driver fails `pnpm check:deps`.
3. **Core never imports a driver.** Drivers register themselves with core.
4. **SDK runtimes mirror each other.** The TypeScript, Python and Rust runtimes have the same modules with the same names, so a fix in one is easy to find in the others.
5. **An SDK holds no server code, and the generator reads only the spec.** `pnpm check:deps` enforces both, along with rules 2 and 3 (`.dependency-cruiser.cjs`).

## SDK runtimes (`sdks/typescript/runtime/`, `sdks/python/channelstack/runtime/`, `sdks/rust/src/runtime/`)

| Concern | Module | Notes |
|---|---|---|
| Transport | `transport` | Bearer token, retries while the server starts, error code → typed exception, a hook that sees every refusal with its request path (`onRefusal` / `on_refusal`, for a test integration), and reads whose refusals skip it (`unreportedRefusals` / `unreported_refusals`) |
| Launcher | `launcher` | `auto` / `attach` / `start`; finding the server binary and its per-platform package name |
| Client base | `client` | What generated handles share: `HandleContext`, the root client's `close`, the version check on connect. | Waiting and polling | `wait` | The one polling loop: cursor reads, timeouts, repeating a call a person would wait for (`retryWhile`), text matching for waits, a pattern as it goes on the wire (Python's and Rust's `pattern_on_wire`: a pattern's flags, inline ones like `(?i)` included, go in `flags`, as the server's patterns are JavaScript's), quiet checks (`untilQuiet`; `watching` makes it look for the whole window, and a timeout names what the agent left open). | Files | `files` | Reading fixture files and directories a test hands over (`readTree`, `readChanges`, `readDocument`; Rust's `read_tree`, `read_changes`, `read_document` on the argument's JSON value, bytes as a list of numbers), and where relative paths start (`setFilesRoot`; Rust's `set_files_root`, the working directory without one); a path that isn't there is an error (Rust's `Error::Files`), not no files |

The Rust SDK is the `channelstack` crate (`sdks/rust`, in the repository's Cargo workspace, toolchain in `rust-toolchain.toml`); its errors are `runtime/error.rs` (a failed check is `Error::Expectation`), its matchers `src/expect/` (see Test integrations), and its launcher, like Python's, finds the binary at `CHANNELSTACK_SERVER_BIN` or `channelstack` on the `PATH`; neither bundles nor downloads one.

## Test integrations (`integrations/`)

| Concern | Module | Notes |
|---|---|---|
| Matcher logic | `integrations/matchers-core/` | Framework-neutral matcher implementations built on the SDK's read methods and `wait`. Vitest's integration adapts it and doesn't reimplement matchers. `toGoQuiet` (decision 0027) is here too: quiet within `within`, with at most `maxReplies` app messages since a person last wrote, naming the authors in turn. pytest's can't import TypeScript, so `pytest-channelstack/matchers.py` is its Python counterpart, and the Rust SDK's `expect` module (`sdks/rust/src/expect/`) its Rust one: the same checks, semantics and messages, kept in step with this module |
| Vitest | `integrations/vitest/` | Plugin (`index.ts`; it sets `testTimeout` above the checks' own wait when the project sets none), attaching to or starting a server (`global-setup.ts`), a session and fixtures per test, registered with `test.override` so a suite's `test.extend` builds on them, the `expect.extend` adapter, and skipping a test live mode can't run, with the reason, and failing a test that left a bot loop, from the quiet route's `loops` (`setup.ts`); a channel's fixture refused live becomes a stand-in that refuses on first use, so only that channel's tests skip (`refused.ts`, `refusedLive` for channelstack's own per-test checks) |
| Checks | `integrations/checks/` | `slackChecks()`, `githubChecks()`, `linearChecks()`, `notionChecks()`, `resendChecks()`, `googleChecks()`, `discordChecks()`: the standard behaviour checks, registered as ordinary tests, built on the public API and the matchers only. `SLACK_CHECKS`, `GITHUB_CHECKS`, `LINEAR_CHECKS`, `NOTION_CHECKS`, `RESEND_CHECKS`, `GOOGLE_CHECKS` and `DISCORD_CHECKS` list their ids. `deliveryOf()` is the one way a check gets its delivery: live there is none, and the check skips with the delivery reason. `app` names any app: the suite resolves it to its handle once (`createApp` for any name but `my-agent`) and every check uses that handle; `<channel>.no-reply-loop` scripts a peer app that answers the agent, and `loopTurns` (default 3) bounds the agent's answers to it (decision 0027) |
| pytest | `integrations/pytest-channelstack/` | The plugin (`plugin.py`): one client per run (`channelstack`), a session per test (`channelstack_session`), a fixture per channel (one for each of the SDK's `CHANNEL_NAMES`), the `--channelstack-mode` option and ini settings, and skipping a test live mode can't run, with the reason, and failing a test that left a bot loop. `expect(subject)` (`matchers.py`): every matcher of matchers-core, with its semantics, options and failure messages, `not_to_…` for negations ([decision 0018](decisions/0018-pytest-expect.md)).
